**Tech Stack：** 沿用 V5 的 TypeScript 前端、Python 后端／规划器、PostgreSQL、工作进程和 Linux 容器沙箱。前端建议 React，后端建议 FastAPI，模型／数据接口以适配器隔离；具体框架是推荐实现，不是新增竞赛指标。

## 1 分工结论

**按四块能力分工，六个场景由这些能力共同组成。从第一条转账链路开始合并，每轮都保持一个能运行的共同版本。**

| 成员 | 建议匹配能力 | 主责与边界 | 独立可展示的交付 |
|---|---|---|---|
| A：交互与卡片负责人 | 擅长前端、产品流程、接口，能完成常规后端 | 两客户端、意图澄清、确认／强验证交互、结果展示、卡片应用层、体验与演示材料 | 用户能提出需求、确认真实参数、查看真实业务状态；卡片申请到挂失完整流程 |
| B：交易内核负责人 | 擅长后端、数据库、事务、并发与故障排查 | 身份、账本、资金预留、授权消费、转账、调度、申购赎回订单、回执对账与部署 | 不依赖大模型，通过 API 完成单笔交易、并发防重、超时恢复和正确记账 |
| C：金融分析与业务负责人 | 擅长 Python、数据、金融规则及 StockQuant | 账单、风险测评、产品比较、量化适配、订阅／商户、AA、数据与统计报告 | 固定输入产生可复算账单／风险结果；商户、订阅和 AA 有持久业务状态 |
| D：规划与系统验证负责人 | 擅长 Agent、状态机、算法与系统设计 | DAG 规划、运行时策略、增量恢复、沙箱、审计、评测框架、集成协调 | 给定目标与变化事件，生成合法计划，执行／停止／修复；判定最终业务是否达标 |

由团队指定一人兼任协调人，默认 D 组织技术联调；行政报名和提交由实际队长负责。协调人负责安排问题归属与合并顺序，模块缺陷由原负责人修复。

V5 主责保持一致：A 22 项、B 26 项、C 22 项、D 22 项。数量不等于工作量：B 的事务与异步执行较复杂，D 的规划和评测也较复杂。本计划把场景应用层、提供方服务、数据和用户测试交给 A/C，减少内核负责人承担全部场景的风险。

## 2 全员共同遵守的规则

- 所有表内 V5 需求均为完整版本必做；按质量门槛推进，不按十一天缩减六场景。
- 银行金额一律采用整数人民币分 `amount_minor`，币种固定 `CNY`；输入小数最多两位，禁止用浮点更新余额。
- 时间以带时区 ISO 8601 保存，持久化 UTC；业务日和日累计采用 Asia/Shanghai。
- 用户身份来自认证会话；请求体或模型输出不能覆盖 user_id、权限等级或业务结果。
- GREEN 查询按政策直接执行；订阅查询保留官方 YELLOW 例外；日累计转账超过 1000 元需要 RED 强验证。
- 一个逻辑写操作在重试、恢复、跨渠道中使用同一 operation_id；余额和授权消费由 B 的内核事务处理。
- 超时保留 unknown/pending，先查原订单；未到账退款、赎回和 AA 不算可用资金。
- 外部文本和模型生成计划不可信；最终检查在服务端，卡片／订阅等非资金写入也经过统一执行入口。
- 精确授权绑定参数和修订；范围授权必须满足子集验证、累计额度和次数，不得生成新操作来重置额度。
- 每个模块提交功能、测试、契约、运行说明及证据；Mock、离线重放和在线运行明确标记。
- 本计划中的代码目录、函数和命令是未来仓库约定，不代表这些代码现在已经存在。已有 StockQuant 保持独立，通过只读适配器调用。

## 4 必须先冻结的模块契约

### 4.1 第一轮共同交付

四人先共同完成一份可运行的契约样例包，再各自扩展。包中至少包含下表类型、Schema 正反例、工具登记、状态枚举、错误码、种子数据和运行模式标识。API 文档必须能从代码或同一契约源生成／校验，防止维护两套字段。

| 契约 | 必需内容 | 主责 |
|---|---|---|
| AuthContext | 服务端身份、角色、渠道、会话引用；不能由模型自由构造 | B |
| GoalSpec | task_id、revision、reference_time、goals、hard_constraints、preferences、unresolved | A |
| ExecutionPlan | plan_id、task_id、revision、steps、dependencies、read_set、write_set、expected_effects、compensation_policy | D |
| Snapshot | 账户／保护组、余额、预留、冻结、政策／条款／报价版本与 observed_at | B；C 提供产品／报价部分 |
| OperationDraft | operation_id、task_id、plan_revision、tool、typed_args、parameters_hash | B；D/C 提供候选内容 |
| Grant | 用户、范围哈希、原修订、验证等级、有效窗口、额度／次数、状态 | B/D |
| PolicyDecision | allow、required_level、reason_codes、policy_version；只有可信服务端生成 | D |
| OperationView | operation_id、状态、费用、提供方引用、回执、版本、待处理事项 | B |
| DomainResult | 类型化数据、来源、计算／条款版本、可用时间及 warnings | C；卡片由 A |
| TaskResultView | 已完成效果、未完成项、当前等待原因、用户下一步操作 | A；D/B 提供权威事实 |

### 4.2 内部接口约定

这些是各模块要实现的接口名称与输入输出约定，具体 JSON 字段以上述 Schema 和 V5 为准。AuthContext 只在可信服务端传递；对外 API 不接受客户端自行声明的可信身份。

| 提供方 | 接口 | 使用方及限制 |
|---|---|---|
| A | `compile_goal(context, message, history, reference_time) -> GoalSpec` | D 消费结构化目标；有 unresolved 时等待澄清 |
| B | `get_snapshot(context, account_ids, task_id) -> Snapshot` | C/D 查询；不能传别人的账户绕过归属 |
| D | `build_plan(context, goal, snapshot, tool_catalog) -> ExecutionPlan` | A 展示；不能据此直接扣款 |
| D | `evaluate_policy(context, operation, snapshot) -> PolicyDecision` | B 提交前再次调用；初始 UI 级别不是最终凭证 |
| B | `prepare_operation(context, draft) -> OperationView` | D 登记稳定操作 ID；只准备，不消费授权、不产生外部支付 |
| B | `confirm_plan(context, scope_hash) -> GrantOrChallenge` | A 的人类确认入口调用；模型工具目录不暴露此能力 |
| B | `verify_challenge(context, challenge_id, factor_response) -> Grant` | A 专用验证界面调用；验证码不进入 LLM |
| B | `submit_operation(context, operation_id, grant_id, expected_version) -> OperationView` | D 调用；B 原子检查策略、资金、授权和版本，记录消费／占用／Outbox |
| B | `get_operation(context, operation_id) -> OperationView` | A/D 查询；超时恢复沿用同一 ID |
| C/A | `validate_domain(context, operation, domain_snapshot) -> DomainValidation` | D 预检、B 提交时校验；纯确定性规则，不能自行授权 |
| C/B | `ProviderAdapter.submit/query/cancel(stable_operation_ref) -> ProviderResult` | B 工作者使用；适配器须支持稳定键与查询 |
| D | `repair_plan(context, task_id, event) -> ExecutionPlan` | 新修订保留确认效果和未知边界；不能重新生成已支付动作 |
| A | `render_result(task_state, operations, domain_results) -> TaskResultView` | 只显示已核验事实，不根据模型措辞宣称成功 |

其中 `GrantOrChallenge` 只允许 active_grant 或 pending_challenge 两种分支；`DomainValidation` 包含 valid、reason_codes 和校验版本；`ProviderResult` 包含提供方订单引用、状态、已确认效果及回执来源。实际实现中应把这些定义写入 Schema，禁止返回自由文本让调用方猜测。

外部访问的 HTTP 路径沿用 V5 第 16 节，例如 POST /v1/tasks、POST /v1/plans/{id}/confirm、GET /v1/operations/{id}。本计划不另起一套不兼容路径。

### 4.3 第一份共享样例

用合成用户 user_demo_01、账户 account_salary 和两个同名联系人建立快照；账户余额 900000 分，应急金 800000 分，币种 CNY，时区 Asia/Shanghai。转账样例为 10000 分；生日任务预算为 80000 分。每个测试从独立初态恢复，转账样例不会偷改生日案例的余额。

所有人的契约测试使用这份样例，C 提交数据来源／合成声明，B 负责可重建种子与账户数据，A 补齐显示内容，D 补齐期望计划与状态判定。身份验证使用可测试的真实验证器流程；测试专用密钥不得混入演示配置和公开资料。

### 4.4 变更协议

新增可选字段也要通过契约测试。删除／改名、状态含义改变、金额口径改变和权限变化必须同步列出所有消费者；先做兼容提供方，再迁移消费者，最后删除旧字段。未迁移完成前不能把不兼容变更合进 main。契约版本、Schema、示例、测试及文档在同一组 PR 中更新。

## 5 开发顺序与联调节点

不固定每阶段天数。每轮以可演示、可验收的结果结束；可以提前开发不依赖前置实现的模块，但不能跳过退出条件。

| 轮次 | A 的工作 | B 的工作 | C 的工作 | D 的工作 | 共同退出条件 |
|---|---|---|---|---|---|
| R0 契约与仓库 | 两客户端骨架、目标／结果 Schema | 数据模型、内核接口、迁移与身份 | 业务 Schema、共享样例、StockQuant 入口核验 | 工具目录、计划 Schema、CI、集成样例 | 四人在各自环境运行同一契约包；一个仓库可启动 |
| R1 第一条完整链路 | 说“给张三转100元”→澄清→确认→结果 | 一笔实际模拟转账、授权消费、防重与回执 | 联系人／账单样例；AA 与报告纯计算 | 简单计划→策略→提交→结果判定 | 两客户端可看到同一真实订单；重试不多扣；歧义不乱转 |
| R2 六场景并行扩展 | 卡片、问卷与各场景展示 | 定时、强验证、申购／赎回资金和份额 | 账单、量化、订阅、商户、AA | 多步骤 DAG、全局约束、卡控策略 | 六场景分别完成正常、边界、失败流程；共有接口无分叉 |
| R3 跨场景与异常 | 改意、差异确认、部分成功、接管 | 预留、迟到回执、并发、恢复和补偿 | 缺货、变价、取消费、双端取消及实际成本 AA | 增量重规划、撤销、安全锁、沙箱和审计 | 生日、月末资金、卡片异常三任务族完成；未知资金不误用 |
| R4 竞争证据 | 用户实验、体验与性能采集 | 并发／重启／第二适配器、干净部署 | 数据冻结索引、统计、H4 与业务复核 | 基线、消融、判定器、有界验证、攻击集 | 完成 V5 评测协议，输出实测及失败例，修复关键风险 |
| R5 参赛交付 | PPT、视频、简介与整合文档 | README、部署包及版本复现证据 | 数据／量化／许可证和统计章节 | 算法／安全自评／评测章节及发布核对 | 全套材料对应同一版本；队长核准 Q01—Q05 与提交回执 |

R0 是一起定接口，R1 就是真实集成；R5 是最终发布验收。整个过程中保留可运行的主分支，避免把“最后整合”变成第一次连接模块。

## 6 解决相互等待与工作量失衡

| 容易卡住的位置 | 提前解除依赖的方法 | 负责动作 |
|---|---|---|
| A 等 B 的后端 | 用已冻结 Schema 的契约桩搭 UI；R1 接真实内核 | B 交付带状态的接口示例，A 标记 Mock 模式 |
| C 等账户／订单 | 计算器吃冻结 Snapshot；资金动作依赖统一端口 | B 先提供只读快照及操作协议，C 先做纯计算与领域规则 |
| D 等六场景 | 用工具契约和可注入的提供方桩验证 DAG／失败路径 | 各提供者交效果、失败码与补偿条件，D 不写私有场景捷径 |
| B 被所有业务堵住 | A 完成卡片应用，C 完成订阅／商户／AA 与条款；B 专注写入基础 | D 帮写交错反例与契约检查；B 审查金融写入口 |
| D 同时背规划、所有安全与测试 | 每人完成本模块测试与修复；D 汇总规则、运行器及证据 | A 负责 E2E，B 并发恢复，C 数值／统计，D 系统攻击与判定 |
| A 被六场景界面拖住 | 共用确认卡、状态卡、表格、比较卡、错误卡；C 交结构化显示数据 | A 定组件协议；复杂图表仅在说明业务所需时增加 |
| C 原系统接入过重 | 只读包装已有必要能力，先核验可复算结果和许可证 | C 不迁移整个 StockQuant，不重建股票研究平台 |

阻塞一个工作包时，成员继续本角色的独立测试、样例、规则和文档；在看板标明缺哪个契约／输出。协调人处理优先级，不用降低安全或伪造完成来消除等待。

## 7 每个工作包如何交付

全项目拆成 24 个工作包，每人 6 个，详见四份个人任务书。一个工作包可分为数个独立 PR，每个 PR 必须有单一可核验目的；不要把“全部转账＋全部 UI＋全部规划”做成一个无法审阅的提交。

每个工作包遵循以下循环：

- [ ] 读对应 V5 需求与 Txx 测试族，写清输入、可观察结果及禁止效果。
- [ ] 与依赖方核对 Schema、函数、状态和错误码；新增字段先提交契约及正反例。
- [ ] 对资金、安全、计算和状态行为先写能暴露错误的测试，确认它确实能失败；普通可逆文案／布局调整采用适当检查。
- [ ] 实现最小完整行为，以同一接口替换契约桩；实际代码与测试一起审查。
- [ ] 运行本模块测试和受影响契约测试，把操作回执、账本或最终状态作为证据。
- [ ] 提交小 PR，指定非作者复核；合入后运行当前轮集成样例，更新看板与证据索引。

“代码写好了”是开发状态；“另一人可运行、测试有证据、集成通过”才是工作包完成。项目看板使用 planned、in_progress、review、integrated、verified 五种状态，另用 blocked 标签记录依赖；作者不能仅凭自测把关键包直接标为 verified。

## 8 Git 合并与环境协作

### 8.1 分支与 PR

建议 main 为可运行主分支，按工作包开短分支，例如 `feat/a02-goal-compiler`、`feat/b02-authorization`、`feat/c04-subscriptions`、`feat/d03-recovery`。同一人同时处理独立事项时开不同分支；合并前同步 main，避免长时间积累差异。

示例工作流，供未来仓库执行：

```powershell
git switch main
git pull --ff-only
git switch -c feat/b02-authorization
# 完成该工作包的代码与验证后，只暂存本次改动文件
git add services/api/src/finpilot/kernel/grants.py tests/unit/kernel/test_authorization.py
git commit -m "feat: bind authorization to stable operations"
git push -u origin feat/b02-authorization
```

PR 说明必须包含：工作包 ID、V5 需求 ID、接口／迁移变更、验证命令与实际结果、剩余问题、演示方法。资金、授权和策略的修改由 B/D 共同复核；作者为其中一人时，另一人必须审查。统计结果由 C/D 交叉复核；用户结果展示由 A 与数据提供方核对。

合并顺序为兼容的契约 → 提供方实现 → 消费方实现 → 完整集成测试；若必须同一次改接口与消费者，可作为一组原子合并变更审查。D 协调顺序，具备审核条件的成员均可按团队规则合并，避免只有 D 能合并造成瓶颈。

### 8.2 迁移与测试环境

B 维护数据库迁移唯一链。A/C 的领域迁移随 PR 提交，由 B 检查冲突和升级路径；不允许四个人各自重新生成一套数据库。已共享使用的迁移不改历史，新增迁移修正。

每人独立数据库实例或隔离数据库，集成环境独立于个人环境。测试数据必须由种子／快照重建；含资金操作的并行测试使用独立用户与账户或独立数据库。模型凭证放各自未提交的配置中，仓库只放字段说明与不含秘密的示例。

### 8.3 CI 分层

| 检查层 | 何时执行 | 责任与内容 |
|---|---|---|
| 快速检查 | 每次 PR | 格式／类型、Schema、金额／权限／状态单测、契约兼容、密钥扫描；模块负责人维护，D 编排 |
| 集成检查 | 影响执行链的 PR 及每轮合并 | PostgreSQL 事务、真实验证流程、Outbox／提供方、六场景已完成部分；场景牵头人确认 |
| 完整评测 | 候选版本冻结后，以及相关修复需要复核时 | 固定模型／快照／数据集、攻击故障、基线消融、两模型和重复试验；D 运行、C 统计 |

避免每次改文案都运行全部付费模型实验；也不能用只跑 Mock 的快速检查代替候选版本的真实集成验证。测试失败回到对应模块修复，不能删除断言或把任务强改成功。

## 9 四人各自使用 AI 的协作规范

四人可以各自使用 AI，但每次任务上下文必须带上：V5 的相关章节、个人任务书、当前公共契约、允许修改目录、当前分支及验收条件。AI 生成代码后仍由模块负责人理解、运行并提交。

通用指令可写为：

> 按本工作包实现并验证。先阅读对应 V5 需求、共享 Schema 与已有代码，保持接口、金额单位和状态含义一致。只修改本任务负责范围；确需跨模块改动时，在 PR 中列出消费者和兼容方案。不得新增私有授权、私有账本、硬编码演示成功或绕过安全校验。交付代码、相关测试、执行结果、接口影响及剩余问题，不把未运行的测试写成通过。

A/C 的 AI 不自行复制 B 的资金代码；D 的 AI 不替用户生成真实授权；B 的 AI 不重新发明 C 的适当性评分。共享逻辑应调用公开端口。代码、测试和评价脚本由同一 AI 生成时，关键结果还需另一位成员人工构造反例或独立复算。

## 10 测试、隐藏集与交叉验收

| 对象 | 实现／自测负责 | 非作者复核安排 |
|---|---|---|
| 两客户端、澄清和结果展示 | A | D 审任务状态，B/C 核业务数字 |
| 账本、授权消费、转账、调度 | B | D 查并发／权限，C 手算账本与分摊 |
| 账单、产品规则、量化、订阅／商户 | C | A 检查用户问题与显示，B 查资金写入口 |
| 规划、恢复、策略、沙箱、审计 | D | B 查执行和越权，A 查改意／接管，C 查统计 |
| 最终状态判定器 | D | A/B/C 提供“文本成功但状态错误”等反例；判定器必须失败 |

隐藏测试不能由对应模块实现者拿来调 Prompt。A 保管账单／理财／订阅的未见用户任务，C 保管卡片与交互未见任务，D 保管转账／调度故障任务，B 保管规划／恢复的未见组合。跨模块案例指定一个未实现其被检验关键逻辑的保管人；做不到时标为内部已知回归，不冒充隐藏集。

C 管理任务数量、拆分协议、种子和哈希索引，不因此取得自己负责模块的隐藏明文题目；隐藏标签在保管人的受控位置，不进入公共 Prompt 上下文。揭盲修复后这些题转回归，新泛化主张需要新集。团队内部这种隔离仍不等于独立第三方评测，报告应如实说明。

每人提交测试证据格式统一：work_package_id、requirement_ids、test_case_id、commit、数据／模型版本、输入快照、预期、实际、结果、证据位置和复核人。60 个 Txx 是测试族，每人把相关族细化为可执行用例，不把需求表打勾当成测试。

## 11 最终合并与发布验收

最终合并不是复制四份文件夹。需要完成以下可检查动作：

1. 四人确认所有工作包已合入同一候选 commit，契约、数据库迁移和工具目录一致。
2. 另一位成员在干净环境按 B 的 README 安装、迁移、播种和启动；A 验证两个客户端连接同一后端。
3. 对六场景逐一执行正常、边界和失败流程，并查业务状态；S2 账单是只读结果，不要求为了验收而改余额。
4. 执行生日预算变化／缺货、月末资金等待到账、卡片挂失影响既有任务三条跨场景链。
5. 检查强验证、重复提交、日累计并发、未知回执、取消竞争、沙箱、注入和审计；关键问题必须修复后回归。
6. 以冻结版本完成 V5 评测；研究目标未达到时保留负结果，调整主张，不修改原始数据。
7. 四人各交技术／安全／业务／统计章节，A 汇编 PPT、视频和简介；B 检查安装命令，C 核数据，D 核算法及安全说法。
8. 队长关闭 Q01—Q05、核对资格和官方系统、保存提交回执；技术协调人不能替组委会认定资格。

遇到接口不兼容，由提供方和消费者一起修；资金问题 B 牵头；业务口径 C 牵头；卡片应用 A 牵头、限制策略 D 参与；规划恢复 D 牵头；前端真实状态展示 A 牵头。缺陷工单记录现象、状态证据、复现种子和主责，避免“这是对方的问题”长期无人处理。
