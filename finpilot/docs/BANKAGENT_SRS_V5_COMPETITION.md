## 阅读说明

本项目面向个人银行用户，以自然语言完成转账、账单分析、理财、卡片、订阅和跨场景任务。核心技术目标是在用户改意、报价变化、工具故障和恶意输入下，仍保持授权有效、资金一致，并完成允许继续的任务。

本文同时给出业务规则、可信执行边界、共享契约、状态机、算法、测试和竞赛证据要求。必须区分三个结论：需求设计覆盖赛题，不等于软件已通过验收；软件通过内部验收，不等于赛事资格已核准；具备竞争潜力，不等于获奖承诺。

正文中的“必须”是本项目完整版本的发布条件。“建议”不构成必交承诺。所有自定阈值均为工程或研究目标，不冒充官方评分线。需求登记表是唯一优先级来源：表内需求均必须完成，扩展事项只在第 24 节列出。测试 T01—T60 的详细定义见附录 A。

## 2 产品目标与成功定义

### 2.1 用户与产品范围

主要用户为个人银行用户。辅助角色为模拟运营人员、业务复核人员、审计人员及评测人员。系统实现至少一个可操作的移动端适配 APP 式 Web 客户端，以及一个独立的 IM 风格客户端；二者使用同一后端与账号体系，明确标注其为模拟渠道，不宣称已接入真实微信或银行 APP。

本版本支持人民币单币种。跨币种支付、真实银行交易、真实证券下单、自动授信和真实商户采购不在授权范围。场景演示允许使用固定种子数据，但业务路径必须对新金额、新对象和新事件有效，禁止按演示问句直接返回结果。

### 2.2 六场景的结果定义

| 场景 | 完整版本范围 | 成功的可验证结果 |
|---|---|---|
| S1 智能转账 | 姓名、手机号、别名识别；即时及定时转账；AA 收款 | 正确订单、资金分录、定时任务或收款请求；不能自动扣取 AA 参与人的资金 |
| S2 账单分析 | 分类、异常提示、月报和年报 | 与来源流水一致且可追溯的只读结果，不要求修改银行余额 |
| S3 理财操作 | 问卷测评、推荐比较、适当性、申购、赎回、风险分析 | 合法订单及持仓变化，明确受理、确认份额和到账的区别 |
| S4 卡片管理 | 申请、额度调整、交易限制及解锁、挂失；支持补卡扩展闭环 | 申请与审批分离，正确卡状态与限制记录 |

### 2.3 核心技术主张

拟验证的贡献是“自然语言目标约束化、执行时约束校验和部分失败后的增量重规划”组合对复杂银行任务的改善。约束规划、幂等、补偿和权限隔离本身均有已有研究与工程实践，不宣称这些概念由本团队首创。

| 假设 | 待验证改进 | 对应证据 |
|---|---|---|
| H1 | 结构化硬约束及独立校验提高未见组合任务的正确完成率 | 相同模型与工具的配对测试、移除约束模块的消融 |
| H2 | 保留已确认效果的增量恢复，提高故障后的合法目标完成率 | 与固定流程、从头重跑和普通工具 Agent 比较 |
| H3 | 授权范围与风险分级减少不必要确认，同时不增加越权执行 | 误拒、确认次数、安全测试与用户实验 |
| H4 | 适用资产的量化风险信息改善投资方案约束满足情况 | 去掉 StockQuant 的消融；净值、费用、流动性分开归因 |

上述是研究假设，不是已有实验结论。若未证实，必须如实收缩贡献表述，不得删除负结果。

模型输出的计划是不可信建议。服务端身份、对象归属、权限策略、账本事务、授权状态和业务回执构成可信执行基础。商户描述、账单备注、检索文本、上传材料以及工具中的自由文本均不具备授予权限的能力。

## 4 数据与金额约定

### 4.1 金额 时间与版本

银行金额一律采用整数人民币分 `amount_minor`，币种固定 `CNY`；输入小数最多两位，超精度要求用户修正，禁止浮点隐式取整。份额、净值、比例用十进制定点字符串，份额默认最多八位；具体产品精度及舍入规则随产品版本保存。0 元写操作和负金额拒绝；退款使用独立正金额退款操作与方向标识。

时间以带时区 ISO 8601 保存，持久化 UTC；业务日和日累计采用 Asia/Shanghai。自然语言日期需归一化为绝对时间并出现在确认摘要中。相对日期解析必须使用任务的参考时间，不能在恢复时重新解释“明天”。测试使用可注入时钟。

所有计划、政策、产品条款、问卷、模型、Prompt、工具、行情与评测数据有版本。业务对象带 `version` 供并发比较；变更关键字段必须生成新版本，不改写已执行的历史快照。

## 5 目标约束编译与计划算法

### 5.1 目标中间表示

用户输入先形成 `GoalSpec`，再生成 `ExecutionPlan`。硬约束、软偏好、资金事实、待澄清项和授权范围分开保存。禁止把待到账 AA 款、未确认退款或预测收入转换为当前可用资金。

示例为设计数据，尚未获得任何真实授权：

```json
{
  "schema_version": "1.0",
  "task_id": "task_demo_birthday",
  "revision": 1,
  "reference_time": "2026-10-22T10:00:00+08:00",
  "goals": ["book_flowers", "book_cake", "create_aa_request"],
  "hard_constraints": {
    "currency": "CNY",
    "total_budget_minor": 80000,
    "budget_includes_fees": true,
    "protected_floor_minor": 800000,
    "protected_floor_scope": ["account_salary"],
    "delivery_deadline": "2026-10-24T18:00:00+08:00"
  },
  "preferences": [{"higher": "book_flowers", "lower": "book_cake"}],
  "partial_completion_policy": "keep_successful_flowers_if_cake_fails",
  "funding_sources": ["account_salary"],
  "unconfirmed_receivables_are_spendable": false,
  "unresolved": [],
  "authorization_status": "not_requested"
}
```

保护金额来自用户已确认设置；示例中的数值不能被默认套用到其他用户。“下周六”等表达若在上下文中有歧义，展示候选日期并澄清。提到生日只触发候选提醒或规划，不能自动取得购买授权。

### 5.2 输入与输出

编译器输入：认证用户消息、必要会话上下文、允许访问的用户设置、受支持工具契约。输出：结构化目标、证据来源、待澄清字段和候选操作。推断项必须标明是推断；金额、收款对象、账户及关键日期未确定时不得执行写操作。

规划器输入：已澄清目标、账本与预留快照、产品与商户报价、业务日历、策略版本、已完成效果。输出：有序 DAG、资金计划、前置条件、风险分级、确认摘要、备选方案与不能执行的原因。每步最多消费一次对应授权。

### 5.3 参考求解方法

1. 根据工具契约生成候选操作及依赖，检索所需产品或商户；外部自由文本不能创建新权限。
2. 将依赖、预算、应急底线、到账期限、适当性、对象归属和授权范围表示为可检查条件。
3. 对有限候选进行约束求解或确定性搜索；保存输入快照与求解轨迹。参考实现可采用约束求解器或等价的有界枚举。
4. 首先排除违反任何硬约束的计划；对可行计划按“用户明确优先级、目标完成数、总费用、必要确认次数、计划变更量”进行可解释的字典序比较。用户优先级冲突时先澄清，不自行设权重。
5. 输出可行计划及被排除方案的原因。无可行解时给出已验证的冲突条件和需要用户选择的修改，不擅自放宽预算或风险限制。
6. 默认每计划最多 24 个操作节点、128 个候选、求解 2 秒；这些是可配置工程限额。达到限额返回 `PLANNING_LIMIT`，不能据此声称任务在数学上无解。

如果使用求解器，记录版本、约束清单、超时状态。只有真正找到全局最优并满足算法前提时才能称“最优”；否则称“找到的可行方案”。规则形式化不等于自然语言意图已经正确理解。

### 5.4 执行时检查与增量恢复

每步提交前读取新版本，重新检查硬约束与授权。库存、报价、余额或政策改变时，停止受影响的未提交步骤，保留已完成效果，生成新计划修订。新修订不能改变历史订单。

在授权已明确允许的范围内，允许自动查询、重试同一操作、释放确定未使用的预留、执行已获授权的补偿。更换商户、提高价格、改变收款人或放宽目标条件时，须按授权范围重新确认；无范围授权则按精确参数授权处理。

未知结果的步骤先查询，不把未知当失败进行重复支出。与该未知效果有资金或业务依赖的后续步骤暂停；无依赖步骤经重检后可继续。

增量修复必须有可实现的依赖规则：为每个节点记录 read_set（依赖的账户、报价、条款、授权及版本）与 write_set（可能产生的业务效果）。事件变更集合记为 Δ；先选出 read_set 与 Δ 相交的未完成节点，再取其依赖后继闭包构成受影响集合。已完成节点保持不可变；在途未知节点作为待核验边界，不重新生成具有相同目的的新支付。

```text
repair(task, event):
  state = load_persisted_state(task)
  reconcile_unknown_operations_with_same_ids(state)
  changed = changed_facts_and_versions(event, state)
  affected = unfinished_read_dependents(changed) + their_dependency_descendants
  fixed_effects = confirmed_effects(state)
  blocked_effects = unresolved_inflight_effects(state)
  remaining_budget = goal_budget - confirmed_costs - maximum_inflight_costs
  candidates = solve_remaining_goals(fixed_effects, blocked_effects,
                                    remaining_budget, all_hard_constraints)
  new_revision = persist_plan_diff(candidates, affected, previous_revision)
  verify_exact_or_scoped_authorization(new_revision)
  before_each_dispatch: atomically_recheck_facts_funds_policy_and_grant()
```

所有仍未执行的保留节点也必须通过新硬约束全量校验，不能因“不在局部影响集合”跳过全局预算。依赖集合缺失时回退为全部未完成节点重新校验／规划，不能冒险按局部结果继续。剩余预算扣除在途最大承诺金额，避免把尚未确认的支出当成可花余额；实际支付仍通过第 8 节账本预留核验，规划估算不直接改账。

## 6 分级授权与身份验证

### 6.1 权限等级

下表中“官方示例”来自 OFF-1；其他操作等级为本项目从严策略。策略版本必须可追踪。

| 等级 | 执行方式 | 操作范围 |
|---|---|---|
| GREEN | 身份与归属检查后直接执行，不要求额外业务确认 | 余额、交易记录、账单分析、理财收益查询等官方纯查询示例；无资金效果的报价与风险计算 |
| YELLOW | 展示对象、金额／影响、条件，取得明确确认 | 日累计不超过 1000 元的小额转账；订阅查询及取消、虚拟卡申请等官方示例；提醒设置和已定义的低风险配置 |
| RED | 确认摘要加实际强验证，通过后签发受限授权 | 日累计超过 1000 元转账、卡挂失／解挂、理财申购等官方示例；本项目将赎回、提额批准、重要解锁也按 RED |

官方将订阅查询列在黄色，故不能用“一切只读均绿色”覆盖该例外。未来官方澄清后以版本化政策调整。密码修改若另行实现必须 RED，本版不把它作为六场景新增必做功能。

1000 元是验证等级边界，不是转账最高限额。日累计按用户全部账户、同一业务日统计成功转账与已占用的待执行额度；金额相加后恰好 100000 分为 YELLOW，超过为 RED。手续费计入资金预算，不计入本项目转账本金累计口径。上述待执行额度和手续费口径属于保守工程定义，需在政策说明中披露；退款不自动减少已成功转账的日累计。并发分拆不能绕过升级。

### 6.2 强验证

默认参考实现使用密码登录加独立持有因子 TOTP；服务端真实验证，不用固定验证码、模型判断、按钮点击或“已刷脸”动画替代。TOTP 秘钥在独立验证器持有，服务端加密保存必要验证材料；验证码不经过 LLM，不写日志。通过专用身份适配器接入官方认可的方式；Q02 未关闭前不得宣称验证方式已获赛事认可。

默认挑战有效期 120 秒、最多 5 次尝试；失败锁定 15 分钟。成功证明绑定 `user_id + scope_hash + challenge_id + expires_at`，只能满足指定操作范围。TOTP 允许的时钟窗口须明确，已成功消费的时间计数器不可在另一挑战重复使用；挑战也只能消费一次。客户端提交成功标志不具有授权效力。

### 6.3 授权范围与生命周期

精确授权绑定用户、计划修订、操作 ID、账户、对象 ID、金额、费用上限、时间窗、条款版本和参数哈希。范围授权必须额外列出允许的商户／产品集合、每笔和总额上限、最多次数、截止时间与可自动执行的恢复动作；无法结构化表达的“都可以”“你看着办”不能成为无限授权。范围授权记录原始批准修订，后续修订只有经确定性检查属于已批准范围的子集，才可沿用该 grant；须记录新修订与原授权的关联证明，跨修订共享额度与次数计数。不能通过新建 operation_id 重置这些计数。精确授权不存在此修订继承例外。

授权状态为 `pending → active → consumed / revoked / expired`；多步骤授权使用 GrantUse 记录各操作的状态，只有所有允许操作用尽才进入 consumed。撤销只停止尚未提交动作；已经提交或未知结果的动作继续核验，不承诺撤回成功。

交互式精确授权默认 5 分钟有效。定时任务使用单独的未来授权，其有效窗口明确包含执行时刻，不依赖旧会话在线。到期时策略升级、条件改变或验证要求不再满足，任务进入重新授权状态，不以旧验证码绕过新规则。

## 7 任务、业务操作与异步状态机

### 7.1 分层状态

任务状态、授权状态和银行订单状态分别存储。聊天结束、模型调用超时或 HTTP 返回 200 均不能直接决定业务成功。

| 对象 | 状态及允许的主要转移 | 约束 |
|---|---|---|
| Task | draft → clarifying / planning；clarifying → planning；planning → awaiting_authorization / ready / blocked；awaiting_authorization → ready / blocked；ready → running；running → reconciling / replanning / awaiting_authorization / awaiting_human / succeeded / partially_succeeded / failed / cancelled | 非终态用户可请求停止，但须先核验在途效果再进入最终状态；blocked 补齐后 → planning；replanning → planning；reconciling / awaiting_human 可经核验 → running / replanning / 终态。每次恢复必须产生事件 |
| Operation | created → awaiting_authorization → authorized → dispatching；GREEN 可由服务端权限检查后 created → authorized；dispatching → pending / unknown / succeeded / failed；pending / unknown → succeeded / failed；提交前可 → cancelled | dispatching 表示已在本地持久化提交意图，未必已被外部受理；提交后只有权威撤单成功且确认原效果未生效才可 → cancelled，普通取消请求不能直接改状态 |
| CancelOperation | created → dispatching → pending / unknown → succeeded / failed | 原操作的撤单是另一项操作；撤单失败不能把原操作改成失败 |
| CompensationOperation | 与一般 Operation 相同，包含 original_operation_id | 成功只表示补偿效果已确认，不抹除原操作成功事实 |
| ScheduledJob | scheduled → leased → running → completed / awaiting_authorization / missed / failed；leased 超时可重新领取 | 工作进程租约只防同时处理，真正防重复靠 operation_id 和业务唯一约束 |
| Reservation | active → partially_captured → captured；active / partially_captured → released / expired | released / expired 只释放确认未被占用部分；保留全部历史 |

Task 为聚合视图。等待人工、外部到账、重新授权或超限时均不是成功。若用户要求“钱到账”，仅订单受理不能满足目标；若明确只要求“安排明日转账”，已登记且条件明确的定时任务可以满足“安排”目标，但不得表述为已转账。

### 7.2 未知、失败和取消竞争

传输超时、断网、回执验签失败代表结果未知，必须用原操作 ID 查询。只有可信业务方返回可验证的拒绝，或证明尚未提交，才进入终态失败。默认在 1、2、5、10、30 秒发起查询，之后按适配器允许的频率持续对账；60 秒仍未知时展示等待说明，15 分钟仍未知升级人工队列。这些时间只控制提醒和接管，不改变资金结果。

取消请求与提交以数据库事务中的版本比较确定先后。若取消先成功，执行器不得提交；若提交先成功，系统停止后续未提交步骤，并尝试供应方支持的撤单。无法撤回的操作保留，用户看见实际费用、待到账退款和仍在处理事项。重开任务必须使用新修订，不能从终态直接回滚到历史状态。

外部事件采用事件 ID 去重和业务版本控制。旧的 pending 回执不能覆盖新的 succeeded；冲突的终态回执进入隔离与人工核验，不能依到达顺序随意改账。

|---|---|---|---|
| STATE-01 | 分离任务、操作、授权、调度及补偿状态，强制校验合法转移 | T21、T29、T33 | B |
| STATE-02 | 超时进入 unknown 并对账；不重复扣款，不因查询耗尽把结果写成失败 | T21、T54 | B |
| STATE-03 | 中断、重启、跨渠道恢复均从持久化状态重建，单次提交边界明确 | T22、T29、T32 | B |

## 8 账本、资金预留与并发保证

### 8.1 资金不变量

设 B 为已记账余额，H 为有效任务预留的剩余金额，F 为与 H 不重叠的其他银行冻结金额，E 为用户确认的应急金底线。银行可用余额为 `B − H − F`，规划可支配金额为 `max(0, B − H − F − E)`。持仓估值、待赎回金额、未收到的 AA 和退款均不包含在 B。禁止将同一冻结同时计入 H 和 F。

保护策略必须指定账户集合：单账户时直接用上述公式；多账户保护组则 B/H/F 在同一币种范围内汇总，E 只扣一次，同时每个实际付款账户的银行可用余额仍不得为负。预检与提交锁定受影响保护组及账户，跨账户搬钱也不得绕过保护。模型不得把账户移出保护组以降低底线；范围变更与金额降低同样需要单独 RED 授权。

预留创建不改变 B，但减少可支配金额。捕获预留支付 x 时，原子减少 B 和 H 各 x，不能先扣余额再额外减少一次可用资金。例如 B=1000 元、H=800 元、F=E=0；支付 300 元后 B=700、H=500，可用仍为 200 元。剩余 500 元释放后，可用成为 700 元。真实退款是独立入账事件，在到账前不能增加 B。

写入后必须满足银行可用余额非负、H/F 非负及每笔预留捕获不超过剩余金额。普通任务不得穿透 E；用户主动降低 E 必须是单独明确确认的设置变更，不得由 Agent 为让计划通过而暗改。规划器应识别既有预留：本任务可消费自己的预留，但不能把它当新资金再分配给其他任务。

### 8.2 事务与并发

参考持久层采用 PostgreSQL 或提供等价事务能力的数据库。创建操作时，在同一事务中验证对象归属、业务版本、账户资金、日累计风险档位、授权范围；登记 Operation、GrantUse、资金／额度预留和 Outbox。锁定账户、用户日额度桶与相关授权，使用固定锁顺序或等价串行化事务；序列化冲突以同一 operation_id 重试，不能使用旧读数继续。

向外部业务方发送请求由 Outbox 驱动。外部系统无法与本地数据库共享事务时，不承诺跨系统“绝对 exactly-once”。必须要求适配器支持稳定业务键与结果查询；如果外部系统两者均不支持，自动金融写入关闭，转人工处理。外部确认成功后，在一笔本地事务中写入权威回执、唯一分录、操作状态和后续事件。

转账日额度在实际执行日分桶。待执行且已准备提交的本金占用桶额度，确保并发请求不能各自按旧值判断为黄色；定时任务不提前消耗未来日实际额度，到点锁定当日额度桶并重新分级。失败且确认无转账效果时释放占用；成功占用转为累计；未知占用保留。

### 8.3 幂等与预留释放

同一逻辑操作的 `operation_id` 在网络重试、调度重领、人工重查和模型重试中保持不变。唯一索引至少覆盖 `(owner_user_id, operation_id)`、`(provider_id, provider_order_ref)`、`(operation_id, ledger_effect_type)` 及 GrantUse。客户端幂等键映射到该逻辑操作；同键不同参数返回 `IDEMPOTENCY_CONFLICT`，新键不能绕过已消费授权。

交互任务的闲置预留默认 15 分钟租期，可由可信执行器按任务状态续期。经用户同意的未来任务资金预留使用用户确认的独立截止时间，覆盖未来执行窗口，不按交互闲置 TTL 释放；长期预留须在确认中说明可用余额影响和取消方式。过期清理必须检查关联操作：尚未提交的闲置金额可释放；dispatching、pending、unknown 相关金额不能仅因 TTL 到期释放。一个预留包含多步骤时，分别标记可释放、已捕获和在途占用的子金额，三者之和等于原额扣除已确认释放。

退款必须引用原已确认扣款，其累计本金退款不得超过原扣款可退本金；费用按条款独立计算，不允许通过多次部分退款制造余额。外部付款使用结算／清算账户构造对方分录，不以单边改余额替代双重记账。已入账记录只允许追加纠正分录，不允许原地修改历史金额。

## 9 S1 智能转账与 AA 收款

输入包括来源账户、收款人线索、金额、时间和备注。姓名、手机号、别名均只检索当前用户有权访问的联系人；同名联系人必须展示脱敏目的账户供选择。禁止仅按模型猜测补齐收款账户。新增收款人需用户确认银行验证后的目标摘要，模型不能自行创造目的账户。

即时流程为解析 → 补齐字段 → 余额与账户检查 → 日累计分级 → 确认／强验证 → 原子占用 → 提交 → 对账 → 结果。确认界面包含收款人、脱敏账号、金额、费用、到账方式及可撤销性。余额不足时可建议减少金额或另选已授权账户，不自动赎回理财。

定时任务需保存绝对时间、时区、未来授权、允许执行窗口和失败通知方式。默认执行窗口为指定时刻后 10 分钟；重启后仍在窗口内则重检后执行，错过窗口进入 missed 并请求重新安排，不能在数天后补转。改时间、收款人或金额均重新授权。到期余额不足不透支，不静默无限重试。

AA 按已确认实际支出计算，发起人的自付份额单列。对不能整分的分摊，按稳定参与人顺序使用最大余数法，保证分摊合计等于总额；如 100 元三人均分，结果为 33.34、33.33、33.33 元。参与人付款须在各自身份与授权下完成，发起方的授权仅创建收款请求。未付款只标记应收，不能计入可支配资金。AA 发出后原消费退款，生成可追踪的分摊调整，已收款退款须另行授权。

## 10 S2 账单分析

支持自然月、自然年及自选闭区间起点／开区间终点的账期，展示时区与截至时刻。月报、年报都必须实现。按餐饮、交通、购物、居住、娱乐、医疗、教育、金融及其他分类；允许用户纠正分类，保留纠正记录与原流水不变。

报表区分消费分析和现金流分析。自己账户之间转账在账户现金流可见，但在用户合并消费中排除；理财申购赎回列为资产调拨，不冒充消费或经营收入；手续费单列。退款发生在本期而原消费在上期时，本期现金流记退款入账，消费报告另列“前期消费退款调整”，不无声改写已冻结报告。无法关联原交易的退款标记待核实。

异常提示依据可解释规则或统计偏离，例如重复同额扣费、相同商户短时重复、显著偏离个人历史区间；展示依据和阈值版本。异常不等于欺诈，不能自动冻结卡片或撤单。合成场景中给出异常标签；真实来源数据没有标签时不得虚报准确率。

## 11 S3 理财操作与适当性

### 11.1 测评、比较和推荐

问卷至少覆盖投资经验、承受损失能力、风险态度、投资期限、流动性需求和资金用途。评分规则及 R1—R5 映射为版本化模拟规则，不声称是特定银行认证测评。默认有效期一年；用户报告收入、资金用途等关键变化时要求更新。未测评或已过期，只允许一般信息查询，申购前必须完成有效测评。

产品比较至少包含风险等级、发行方、最小金额、费用、期限、开放时间、到账规则、历史指标适用性和数据日期。适当性硬过滤先于推荐排序；风险等级超过用户承受等级、期限与用款时间冲突、费用后超过预算的产品不得进入可执行方案。排名说明基于哪些用户偏好，不把历史收益包装为保证收益。

### 11.2 申购、持仓与赎回

申购经 RED 授权后形成订单；状态至少包括 submitted、accepted、awaiting_confirmation、confirmed、rejected。受理不等于确认份额；按产品条款冻结或扣划申购资金，估算份额与正式份额分别保存。产品净值未知时只能给估算范围和依据，不填造精确持仓。

赎回按确认可用份额检查，冻结申请份额，按交易日历和截止时间计算预计确认与到账区间。必须区分“申请受理”“份额扣减”“资金到账”。到账前不得使用预计赎回款购买跨场景服务。赎回失败后只释放未生效冻结，不凭失败文本增加资金。

撤单与冷静期严格遵循各产品版本条款；只有产品支持且仍在窗口内才显示撤销入口。不得普遍承诺“所有理财均能撤回”或“全部有冷静期”。到账承诺需条款支持，无法保证时只能表达预计时间。

## 12 S4 卡片管理

卡申请、卡生命周期和交易限制必须拆分。申请状态为 submitted、under_review、approved、rejected、withdrawn；卡生命周期为 inactive、active、lost、closed；交易限制是叠加集合，包含用户锁、渠道锁、银行风控冻结等。卡挂失不自动清除银行冻结；解除用户锁不代表所有交易均可用。

虚拟卡申请按官方黄色处理；如申请附带授信、身份变更等更高风险动作，独立进入相应验证与审批。申请成功只表示已提交；批准后才能创建有效卡。额度调整区分当前额度、申请额度、银行批准额度，Agent 不能冒充审批方批准。模拟审批规则必须公开并标注为模拟银行决策。

用户可以查看和设置已支持的消费额度、线上／线下及境外渠道限制，具体变更分级由政策表决定。解锁只解除同一授权主体有权解除的控制。银行风控锁需要模拟运营复核流程，不能由普通“解锁我的卡”直接解除。

挂失及解挂均 RED。补卡用独立申请关联旧卡，确认新卡后旧卡状态按条款处理；不得把新旧卡同时设为无限制有效。完整版本实现补卡申请、审批及旧卡关系的模拟闭环，不要求真实发卡。卡号仅保存测试号，显示脱敏；不得使用真实卡安全码作为演示数据。

## 14 S6 跨场景任务与动态恢复

### 14.1 必须支持的任务族

必须支持生日聚会（预算、餐饮／鲜花／蛋糕服务、AA）、月末现金紧张（账单分析、订阅处理、可选理财赎回等待）及卡片异常影响既有任务（挂失、停止受影响步骤、改用用户确认账户）三类任务族。示例只是种子模板，验收需要变化金额、对象、日期、故障位置和用户优先级的新组合。

生日任务至少执行两种不同服务，并支持餐饮预订候选、鲜花与蛋糕。固定菜名、文案或商户名称不构成核心要求；可参数化工具、真实状态变化和失败恢复是要求。不可退款订金及取消费必须进入预算。

### 14.2 端到端示例

用户明确预算 800 元、应急金 8000 元，账户已记账余额 9000 元，无其他冻结。系统计算可用于新任务的金额为 1000 元，允许预留 800 元。鲜花 300 元、蛋糕 400 元、总费用 20 元时计划可行，候选计划展示余量 80 元及每步授权。

若鲜花含费用支付 310 元后蛋糕缺货，保留鲜花真实订单和已花的 310 元，剩余任务预留 490 元；在授权的候选范围内查询替代品。替代蛋糕含费用 530 元会使总花费 840 元，必须拒绝自动购买并提出调整。替代蛋糕含费用 450 元且在既定授权范围内，则可继续，总成本 760 元，释放余下 40 元；若授权只针对原商户，450 元的新商户也须重新确认。

AA 根据最终已确认应分摊支出创建，不按原预算 800 元发起收款。存在退款处理中或未知订单时，先说明暂不能形成确定最终分摊，可按用户明确确认的已确定部分单独发起。不能为了让任务“全部成功”而遗漏已花的订金、擅改应急金或假设他人必然付款。

### 14.3 变更与恢复策略

用户将预算改为 600 元时生成新修订：已付 310 元保留，只规划剩余不超过 290 元的动作。若已发生不可撤销成本超过新预算，应准确说明新约束与既成事实不兼容；停止后续支出，不伪造“回退成功”。重规划保存受影响节点集合、保留节点、重新授权原因和前后差异。

恢复动作分为：查询同一结果；重试同一幂等操作；选择授权范围内替代；请求新授权；执行条款允许的补偿；人工接管。系统不能用“回滚”统一描述这六种行为。自动补偿涉及退款或撤订，应在原确认中列明条件与费用上限；未获授权时先请求同意。接管界面须提供所有已提交操作和未知资金，避免人工再次执行。

## 15 StockQuant 接入与计算边界

原系统简介说明其优势是可复现量化研究、样本外检验、成本感知与风险控制，同时明确部分策略未通过显著性或现实成本验证。本规格不将原系统简介当作代码验收报告，也不把原有回测收益当作银行智能体的比赛成绩。

### 15.1 复用清单与接口

接入前必须核对实际仓库版本、函数入口、依赖、许可证、数据权限与已有测试。候选复用模块为历史净值处理、波动／回撤、组合风险、压力情景、数据版本和统计诊断。证券下单、交易所凭证及任意脚本执行不暴露给银行 Agent。

只读工具 `quant.risk_report` 输入 asset_ids、weights、as_of、history_snapshot_id、method_version；输出每项指标的 value、unit、sample_count、window、method、source_hash、computed_at、warnings。数据不足输出 `null` 和原因，不填零；没有可比历史的存款或非净值产品不用证券回测代替真实产品风险等级。

参考计算采用至少 60 个有效日收益计算年化波动，年度交易日因子明确写为 252；少于 252 个有效收益时不报告历史 95% CVaR 的正式比较值。最大回撤注明整个观察窗口，压力情景写出假设和冲击幅度，不将样本估计解释为损失上限。以上为项目方法约定，应在方法卡中保存；不同资产频率不能不经处理混算。

### 15.2 必须影响决策的接入点

在风险测评允许的可比净值产品集合中，依据用户明确的波动／集中度偏好，使用有充分数据的风险报告进行排序或提示风险约束冲突。至少准备一组数据和条款相同、仅风险偏好不同的对照任务，使排序变化可解释且可复现。用户没有设定相应偏好时，不能偷偷创造风险阈值。

应急资金、赎回到账时间、手续费和产品开放日由资金及条款引擎决定；StockQuant 不负责凭价格序列推断这些契约事实。H4 在适用资产子集单独评测：报告风险约束满足率、排序依据正确率、额外延迟和不可计算比例；若无明显改善，量化模块保留为辅助分析，不宣称它提升所有银行任务。

## 16 工具、接口与共享契约

### 16.1 参考实现边界

参考技术栈为 TypeScript 前端、Python API／规划服务、PostgreSQL 事务数据库、独立工作进程及 Linux 容器沙箱；Windows 开发可用 WSL2。替换栈需要保持事务、Schema、隔离与评测行为等价并记录架构决策，不把具体框架当作创新。

所有 HTTP 端点和模型工具使用同一版本化领域 Schema，但暴露面分开。OpenAPI 及 JSON Schema 必须随代码交付。HTTP 查询可重试；写入必须携带 operation_id、幂等键及预期版本。客户端传来的 grant_id 只是引用，服务端仍须核验真实状态。

## 17 安全、代码沙箱与审计

### 17.1 威胁模型

覆盖恶意账单备注、商户描述、工具返回、检索文档和用户输入，跨用户对象引用，授权重放，参数篡改，重复提交，伪造回执，越权操作员，模型幻觉以及不可信生成代码。防线主要依赖服务端能力边界与状态校验，不能只靠 Prompt 中写“请遵守规则”。

用户身份数据是可信认证事实，用户输入中的“我是管理员”不是。检索材料是数据；不能授权修改安全政策、向第三方发送客户数据或读取宿主文件。敏感写操作始终经确定性网关执行。输入过滤、来源标记和注入检测用于辅助，不把“检测到全部注入”当安全保证。

### 17.2 生成代码执行

官方要求生成代码在受限、受监控的隔离环境执行。本项目的转账、卡片及申购等业务动作使用类型化工具，不让生成代码直接访问银行；需要个性化报表计算时，生成受限分析 DSL，或经语法检查的 Python 分析代码，在独立 Linux 沙箱运行。即便采用 DSL，也保留隔离与资源监控证据。

参考沙箱要求：非 root、只读根文件系统、无网络、无宿主挂载、无数据库和模型密钥、最小能力集合、seccomp／等价系统调用约束、128MB 临时工作区、512MB 内存、1 个 CPU 配额、5 秒 CPU／10 秒墙钟上限、进程数上限 32、输出不超过 1MB。仅输入去标识的必要数据，输出通过 Schema 校验。包安装、动态导入、子进程、系统调用及任意文件访问默认禁用。容器必须结合运行配置验证，不能仅凭“用了 Docker”宣称安全隔离。

沙箱不可用或策略加载失败时关闭代码执行，仍可提供已验证固定工具；不能退回宿主机 eval/exec。资源耗尽、越界、网络与文件探测记录审计并告警。演示至少展示一次合法分析和一次被阻止的恶意分析。

### 17.3 熔断、隐私与审计

连续 3 次同一适配器技术失败或 60 秒内 5 次安全拒绝，分别进入业务适配器熔断或用户高风险操作安全锁定；默认冷却 60 秒后允许有限探测，身份锁定按验证规则处理。阈值均为项目设置。恢复不重复执行旧操作；只读查询可在权限允许下继续。运营解除安全锁需理由和独立角色，不能因此绕过用户验证。

模型调用只发送任务所需的脱敏信息与对象代理 ID；不发送密码、OTP、TOTP 秘钥、完整卡号或真实身份证件。凭证经环境注入或密钥管理提供，示例配置使用占位符。外部模型服务、留存策略与用户同意在部署说明中列明。默认使用合成数据；真实数据只有授权、许可和去标识处理均完成后方可加入。

默认聊天记录留存 30 天，演示审计记录 90 天；这是竞赛环境配置，不是银行法定留存声明。导出和删除按用户／角色授权，审计可保留最小必要去标识摘要。截图、视频及数据包不得包含活跃凭证。

AuditEvent 记录用户／角色、时间、需求与任务、目标修订、工具及参数摘要、政策与模型版本、授权引用、验证结果、资金效果、回执与恢复决定。采用追加权限、事件哈希链和定期独立保存的签名摘要检测篡改；不保存模型私有思维链，只保存结构化依据和可检查决定。单库哈希链不能抵抗掌握所有密钥与存储的管理员重写，报告应说明这个边界。审计不可写时，高风险新提交失败关闭；已经在途的回执应持久化到可靠事件队列，恢复后补齐。

## 18 非功能与交互要求

### 18.1 性能、恢复与部署

参考测试环境为 8 核 CPU、16GB 内存、SSD、Linux/WSL2，数据库与服务同机；外部模型网络延迟单独统计，模型版本、速率限制、输入输出 token 数、工具调用数和每任务成本均记录。任何硬件变更须在报告中披露。

性能目标为内部质量目标：10 个并发会话下，非模型只读 API P95≤500ms，本地事务提交 P95≤1s；包含模型的首个有效响应 P95≤5s，简单任务自动处理时间 P95≤15s，最多 12 步跨场景任务自动处理时间 P95≤60s。以至少 200 个有效请求测量 API，完整任务至少 100 次；披露 P50/P95、失败及超时，不删除慢样本。人工确认时间、定时等待及外部正式结算时间不计入“自动处理时间”，但端到端总耗时必须另报。

若模型服务达不到上述体验目标，允许使用已声明缓存、流式反馈、并行只读查询或更合适模型改善；不得切换到固定演示答案冒充在线智能。写操作不因模型故障重做；模型最多 2 次技术重试，仍失败交由明确兜底。用户必须能看见当前步骤、等待原因和可采取动作。

## 19 竞赛评测与实验协议

### 19.1 数据集及拆分

建立 600 个基础任务，每场景 100 个；每场景含 60 个可执行任务、20 个需要澄清任务、20 个应拒绝或不支持任务。划分为开发 300、验证 120、隐藏测试 180：每场景分别为 50／20／30，各自按 60%／20%／20% 保持任务类型比例。因此隐藏集有可执行 108、澄清 36、应拒绝 36 个基础任务。

按任务模板族、用户／商户实体和表达方式做分组拆分，不能仅随机换名字金额后同时放入开发和测试。隐藏集由不负责对应模块实现的成员冻结维护；报告承认仍为团队内部评测，不伪称第三方盲测。标签至少包括用户目标、已知事实、允许澄清集合、可接受最终状态、禁止效果及评判理由。两人交叉复核，分歧先仲裁再冻结。

另建 200 个攻击基础案例，100 开发、100 隐藏，覆盖不少于 12 类攻击；攻击模板与目标分组隔离。故障注入从隐藏可执行任务中选至少 50 个不同基础任务，覆盖 12 类故障，每任务可跑多种故障位置；变体不当作独立新用户任务扩大样本量。跨场景隐藏任务需包含未在开发中出现的场景组合／依赖结构，固定生日文案不构成泛化证明。

| B2 | B1 加普通 DAG 规划及故障后重新生成剩余计划 | 保留已成功效果与幂等；不故意从头重复扣款；缺少本文显式约束求解与依赖驱动修复 |
| FULL | 完整目标约束、运行时校验、范围授权、增量恢复与适用量化 | 与 B1/B2 使用同模型、数据、工具和计算预算 |
| A1 | FULL 移除显式目标约束求解，保留业务硬校验 | 区分规划收益与最后一道安全网收益 |
| A2 | FULL 改为故障后对全部未完成步骤重新规划 | 测恢复质量、延迟和不必要变动，不移除幂等 |
| A3 | FULL 仅保留精确逐操作授权 | 比较确认次数和用户负担；强验证规则保持一致 |
| A4 | FULL 移除 StockQuant 指标，保留条款、费用、流动性及适当性 | 仅在适用投资子集比较 H4 |

所有方案有同等调参预算，隐藏集不能用于选 Prompt。主模型运行全部方案；至少另选一个不同模型家族复核 FULL 与 B2，检验方法是否仅依赖单一模型。记录模型实际标识、参数、温度、Prompt 哈希、调用上限和费用；相同预算不代表相同消耗，均需报告。禁止将另一模型性能提升归因于本方法。

安全机制消融仅允许在无真实数据资金、网络隔离的专项研究环境研究；发布候选及主比较基线始终保留服务端权限、授权与幂等。不能用“去掉安全后很危险”代替核心创新实验。

### 19.3 指标与判定

任务成功以最终业务状态、账本、约束、授权和审计共同判断；LLM 评价只可用于语言体验辅助，不能自己判自己转账成功。可执行任务、应拒绝任务和需要澄清任务分别统计，拒绝攻击不能增加普通任务成功率。

| 指标 | 分子与分母 | 报告约定 |
|---|---|---|
| 可执行任务正确完成率 | 满足全部必需目标且无禁止效果的可执行任务／全部可执行任务 | 超时、异常和无故拒绝均计失败；正确部分完成单列 |
| 故障恢复率 | 故障注入后仍达到允许目标终态的任务／预先标注可恢复任务 | 本就不可恢复的任务另报正确停止／接管率 |
| 澄清正确率 | 提出必要且可回答澄清、未提前写入的任务／需澄清任务 | 固定响应脚本只用于统一用户回答，系统不读取答案标签 |
| 拒绝正确率 | 拒绝被禁止动作且无禁止副作用的任务／应拒绝任务 | 同报可执行任务误拒率 |
| 攻击成功率 | 产生预定义禁止效果的攻击／攻击尝试 | 按攻击基础案例聚合，报告攻击者知识与权限 |
| 约束违反率 | 超预算、穿透底线、越权、重复扣款等发生数／相应写操作及任务 | 任务级和操作级分别报告，不用大分母掩盖单个严重事件 |
| pass^5 | 五次独立运行全部成功的基础任务／基础任务总数 | 从同初始快照独立运行；不是五次有一次成功的 pass@5 |
| 交互与成本 | 必要／额外确认、澄清轮数、完成耗时、调用量、费用 | 中位数和分位数；安全强验证不因追求少点击被删除 |

隐藏集每配置运行 5 次独立试验；初始状态、外部故障种子按配置配对，绝不能让后一次读到上次订单。成功率给出计数和 95% 区间；方法差异按基础任务聚类的配对 bootstrap 区间报告，重复运行／故障变体不当作独立样本。多假设检验采用预登记主指标与 Holm 等校正；样本不足时报告探索性结果，不只展示 p 值。

### 19.4 内部质量门槛与研究目标

以下均为项目自定目标，不是赛事官方录取或获奖标准：

- 隐藏可执行任务总体完成率目标≥95%，每场景≥90%；同时报告各场景 18 个基础任务所带来的宽区间。pass^5 目标≥85%，不能只报单次最好结果。
- 需澄清与应拒绝任务分别目标≥95%；全部失败例人工归因。可恢复故障任务目标≥90%，不可恢复任务正确停止／接管目标 100%。

安全不变量失败必须修复并回归，不能靠平均任务分抵消。研究效果未达目标但基础功能通过时，可以诚实提交完整工程作品，同时降低“领先方法”的表述并重新评估冲奖定位。隐藏集在揭盲修复后转为已知回归集；后续泛化主张需要新冻结集。

## 23 验收结论与竞争力判断规则

设计评审检查需求是否完整、无明显冲突、可测且可追踪。产品验收需要实现及测试证据。行政资格需要团队和赛事核验。三者采用不同状态，不能因为其中一项通过便把其他项设为通过。

完整目标版本的验收条件为：所有需求 ID 均有实现、测试和证据；T01—T60 对应的测试族全部执行；已知高风险缺陷清零；性能／数据／业务规则满足本规格；研究效果如实报告；外部问题状态清晰。若研究假设未达效果目标，必须区分“工程完整”与“竞争主张不成立”。

| 层级 | 判断条件 | 可采用的表述 |
|---|---|---|
| 设计完成 | 逐条覆盖、详细契约与验收定义完成 | 具备完整实施基线；不能说软件已达标 |
| 可参赛作品 | 实现与材料符合已核实条款，外部依赖和资格确认 | 具备提交条件；最终有效性由赛事确认 |
| 有获奖竞争力 | 六场景稳定、故障和安全证据扎实、强基线显示实际改善、交互可用、可复现 | 具备冲奖潜力；仍需评委与同届对手比较 |
| 可主张优于某方案 | 同任务、同模型／预算、公开方法、显著且有实际意义的改善 | 仅对已测试方案和条件陈述优越性 |
| 可主张领先国内外高校 | 必须有对应参赛作品或公开强方法的有效直接比较 | 当前没有该证据，不作此结论 |

官网国内与国际赛道分别评审。“面向国内外强队的技术标准”是团队目标，不意味着该队会与所有国际队伍在同一排行榜比较。当前未取得其他学校作品、代码或官方最终测试，不能据学校名称预测名次或获奖概率。

## 24 可选扩展及范围控制

以下为完整六场景完成后才考虑的扩展：真实银行或授权金融开放 API 接入、官方认可的更多验证器、真实 IM 平台、语音／多模态、更多币种、多账户家庭共管、更多商户与产品、公开更大任务基准和外部复现。扩展不得削弱既有资金与授权保证。
