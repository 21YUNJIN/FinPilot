# S3 理财模块：用 StockQuant 做底层，还是用 FinPilot 自带？

日期：2026-10-28  
范围：六场景中的第三模块 S3「理财操作与适当性」，对应 `BANKAGENT_SRS_V5_COMPETITION.md` 第 11 节与第 15 节。  
结论依据：V5 规格、四人分工包（C03）、2026-10-28 对比评审、StockQuant 2026-10-28 技术报告、以及本机 StockQuant 备份（HEAD 5559e3f）的实际代码。

## 1 结论

**用 StockQuant，但不是原样搬进去，而是把它改造成"只读净值风险内核"；FinPilot 自带的适当性、条款、费率、流动性、份额与资金执行继续由 FinPilot 负责。**

一句话分工：

```text
FinPilot（银行产品层）                     StockQuant 银行版（只读计算层）
风险问卷 / R1—R5 适当性硬门槛   ───────▶   不参与，只接收"用户可承受等级"
产品条款 / 费率 / 期限 / 赎回到账 ───────▶   不推断，只使用调用方给的字段
申购 / 赎回 / 份额 / 资金 / 回执  ───────▶   完全不接触
                                          净值波动 / 回撤 / CVaR / Sharpe
                                          压力情景 / 可复现排序证据
```

这不是"二选一"，而是把第三步拆成两种职责：**决策约束归银行，风险度量归量化系统**。V5 第 15.2 节已经写死了这条边界（应急资金、赎回到账、手续费、开放日由资金及条款引擎决定），本实现只是把它落成代码。

## 2 为什么不能"全内置"

FinPilot 当前的量化相关代码不在比赛主线上：

| 现有代码 | 实际能力 | 对 S3 是否够用 |
|---|---|---|
| `bankagent/quant_adapter/adapter.py` | `factor_snapshot`（个股因子 z 分）、`portfolio_risk`（CSI300 行情组合波动） | 不够：输入是股票代码和股数，不是理财产品净值；`backtest_summary`、`stress_test` 直接 `NotImplementedError` |
| `bankagent/finance/metrics.py` | 营收增速、毛利率、ROE、DCF | 不够：这是企业投研口径，不是净值产品风险 |
| `bankagent/valuation`、`risk/reverse_challenge.py` | 估值与反方质询 | 与产品风险指标无关 |

也就是说，"内置"目前没有可用的 S3 风险计算，只有股票因子接口。若沿用内置，C03 要新增净值序列处理、指标口径、样本量门槛、压力情景、来源追踪，等于重写一套量化统计——这正是 StockQuant 已经做过并测试过的部分。

## 3 为什么不能"全用 StockQuant"

StockQuant 原样是**股票/可转债/ETF 研究系统**，它的强项和 S3 的需求并不重合：

| StockQuant 现有能力 | 与 S3 的关系 | 处理方式 |
|---|---|---|
| 因子、选股、组合优化、回测 CAGR | 银行理财不选股、不承诺收益 | **不接入**，只保留风险统计 |
| 依赖 5.5 GB `data/real` 行情 | 银行产品是产品净值，不是 A 股行情 | 改为**调用方传入产品净值**，服务不碰行情库 |
| `data/real` 在备份中未导入 | 本机无法复现股票链路 | 正好：新服务不依赖它 |
| 回测收益、DSR/PBO、alpha 主张 | 评审已指出未通过门槛，不能当比赛成绩 | **不进入**银行产品页，不引用 |
| 下单、QMT、券商凭证、Paper 执行 | 银行 Agent 不得调用 | **物理隔离**：新服务不 import `execution`，无下单函数 |
| MIT 许可 | 可复用、可修改、可分发 | 保留版权声明即可 |

如果直接把 StockQuant 的"回测收益/因子选股"塞进 S3，会同时违反 V5 的 QUANT-04（不输出收益保证）和评审对"用回测 CAGR 当宣传"的批评。

## 4 改造清单：把"股票量化系统"改成"银行理财风险服务"

已在 `s3-quant-service/` 落地（60 项测试通过，证据见 `docs/EVIDENCE.md`）：

1. **输入银行化**：`symbols/positions` → `products[].nav[]`（日期 + 净值），另带官方风险等级、费率、期限、赎回到账、起购金额。
2. **输出银行化**：按 V5 §15.1 输出 `value / unit / sample_count / window / method / na_reason`，另加 `source_hash / computed_at / method_version`。
3. **口径守卫**：≥60 个有效日收益才算年化波动（252 因子）；<252 个收益不报正式 95% CVaR；最大回撤标注整个观察窗口；数据不足返回 `null` + 原因，不填 0。
4. **压力情景**：只做透明一阶情景（净值冲击、样本内最差 20 日重放、波动×2 参数情景），每条都写假设，并声明"不是损失上限"。
5. **可以影响决策**：先过硬约束（风险等级、期限、流动性、起购），再按用户明确偏好排序；同时输出 A4 消融排序（移除量化指标），供 H4 直接比较。
6. **可追溯**：每个产品净值做 SHA-256，客户端独立复算并比对；方法版本固定为 `sq-wealth-risk/1.0.0`；服务端审计日志记录 request_id、响应哈希、延迟。
7. **服务化隔离**：独立进程 + Bearer 令牌 + 限流 + 4 MB 体积上限；FinPilot 侧只放一个 HTTP 客户端，不 import StockQuant。
8. **降级有语义**：量化不可用时，若指标只是说明 → 标 NA 并继续用条款/费用排序；若指标是硬风险条件 → 阻断该产品决策。绝不把"没数据"当"低风险"。

## 5 与 V5 需求的对应

| 需求 | 本实现如何满足 | 状态 |
|---|---|---|
| QUANT-01 真实代码与依赖、只读适配、可追溯版本 | 真实 import `stockquant.backtest.metrics`；`/v1/meta` 与每个响应带引擎版本、commit、方法版本、source_hash | 已完成（合成数据联调） |
| QUANT-02 固定数据与方法可复现；不足/不适用返回 NA | 输入哈希 + 固定口径；60/252 门槛；`na_reason` 明确 | 已完成 |
| QUANT-03 实际改变筛选/排序，并做 H4 消融 | `rank` 接口同时返回量化排序与 A4 基线排序、`rank_changes` | 管道已完成；真实用户/产品上的 H4 尚未跑 |
| QUANT-04 市场风险、适当性、流动性分开；不输出收益保证 | 三者是不同字段；官方等级不被统计档替代；免责声明固定随响应返回 | 已完成 |
| S3-02 比较展示风险、费用、期限、流动性、出处，排序受硬约束限制 | `hard_filter_reasons` 先于打分；`ranked[].metrics_brief` + `data_window` + `warnings` | 已完成（展示层由 A 接） |

## 6 需要团队确认的三件事

1. **真实净值来源**：比赛环境只能用合成产品。合成数据必须在界面标注；若未来接真实产品，需补数据授权与净值披露口径（评审 §5.4 已点名"StockQuant 真实接入未证明"）。
2. **量化在 UI 中的位置**：建议放在"比较"页的风险列与"为什么这样排序"里，不放在收益宣传位；产品卡必须同时显示费用、期限、到账和风险指标日期。
3. **硬门槛归属**：如果银行方要求"风险指标不达标即不可申购"，把 `RiskGate(require_metrics_for_ranking=True)` 打开，由 B 的订单前置条件消费；这是策略决定，不能由模型临时决定。

## 7 一句话回答

第三步用**你的 StockQuant 做底层计算**，但只保留它的风险统计与可复现纪律，砍掉选股/回测/交易；银行侧的适当性、条款、费用、流动性和资金执行仍用 FinPilot 自带逻辑。这样既有你系统的技术含量和证据链，又不会让量化模块越过银行规则去"推荐产品"。
